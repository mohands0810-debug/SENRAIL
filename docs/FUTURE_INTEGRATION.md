# SENRAIL — Future Integration

## Overview

SENRAIL's architecture is explicitly designed with a future authorised railway data integration in mind. This document describes the integration pathway, the interfaces that must be implemented, and the components that remain unchanged.

---

## Current Architecture (Prototype)

```
Synthetic Train State
        │
        ▼
Simulation Engine (engine.ts)
  - Maintains train position, speed, delay
  - Applies scenario presets
  - Generates operational events
        │
        ▼
SENRAIL Processing (AppContext.tsx)
  - Collects updated train state
  - Extracts features
        │
        ▼
ETA Prediction Engine (etaPredictor.ts)
  - Computes remaining time
  - Applies condition effects
  - Returns ETAPrediction + contributing factors
        │
        ▼
Dashboard / API Layer
```

## Integration Points

### 1. Train Position and Speed Feed

**Prototype:** Simulation engine generates updates every 3 seconds.

**Production:** Subscribe to a streaming RTIS-compatible feed providing:
```
{
  trainId: string,
  currentSpeed: number,       // km/h
  currentDelay: number,       // minutes
  currentSection: string,     // section identifier
  distanceRemaining: number,  // km to destination
  timestamp: ISO8601
}
```

**Integration file:** Replace the update logic in `src/simulation/engine.ts → updateTrains()` with a feed subscription handler.

---

### 2. Operational Event Feed

**Prototype:** Events are generated by `buildOperationalEvents()` based on the active scenario preset.

**Production:** Subscribe to an authorised operational event stream providing:
```
{
  eventId: string,
  sectionId: string,
  type: "Congestion" | "Track Maintenance" | "Speed Restriction" | "Signal Hold" | "Weather",
  description: string,
  speedRestriction?: number,
  startTime: ISO8601,
  endTime: ISO8601 (estimated),
  status: "Active" | "Upcoming" | "Cleared"
}
```

**Integration file:** Replace `buildOperationalEvents()` in `src/simulation/engine.ts` with an event feed normaliser.

---

### 3. Historical Data Feed

**Prototype:** 15 synthetic records in `src/data/staticData.ts`.

**Production:** Query a historical data store:
- Average sectional travel time by train, section, day, time, weather, and congestion
- Could be a database query, a pre-computed lookup table, or an ML model serving average predictions

**Integration file:** Replace `getHistoricalBaseline()` in `src/data/staticData.ts` with a service call.

---

### 4. Weather Data

**Prototype:** Weather is scenario-controlled.

**Production:** Subscribe to a weather observation or forecast feed indexed by railway section or geolocation. Abstract behind a `WeatherService` interface:

```typescript
interface WeatherService {
  getWeatherForSection(sectionId: string): Promise<WeatherCondition>;
}
```

## API Endpoints (Future Backend)

When a backend is introduced, `src/services/api.ts` becomes HTTP client calls to:

```
GET  /api/trains                     → Train[]
GET  /api/trains/:id                 → Train
GET  /api/trains/:id/eta             → ETAPrediction
GET  /api/route-conditions           → RouteSection[]
GET  /api/events                     → OperationalEvent[]
GET  /api/trains/:id/eta/history     → ETAHistoryPoint[]
POST /api/simulation/scenario        → SimulationState (dev/test only)
```

The UI layer calls these service functions and does not change when they are backed by real HTTP calls.

## Deployment Considerations

### Streaming vs. Polling

For production, a streaming architecture (WebSocket or Server-Sent Events) is preferable over polling for train position updates. The 3-second tick interval in the simulation engine models a similar frequency.

### Latency

The ETA prediction engine is synchronous and computes in under 1 ms per train. For a fleet of hundreds of trains, predictions can be computed server-side and cached.

### Scalability

- The prediction engine is stateless and pure — it can run in parallel across many trains
- Session-level state (selected train, simulation controls) remains frontend-local
- Shared state (train positions, events) moves to a real-time backend

### Security

- Authorised railway data feeds require authenticated API access
- No API keys or credentials should ever be committed to the repository
- Use environment variables for all credentials (see `.env.example`)
